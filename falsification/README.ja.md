# 取引モデル反証記録 / Trading-model falsification journal

このディレクトリは一つのことだけを行います。「取引で正しいモデルとされている主張」を検証可能な命題に書き換え、再現可能な計算で**反証を試みる**。反証できなければ「証拠不足」と正直に書き、検証していない結論を既定の正しさとして残しません。

対象は二種類あります：

- 本リポジトリのツールと手法に暗黙に含まれるモデル（価格付けの口径、年率換算の口径、バックテストの仮定、合議投票の仮定など）；
- 広く流布しているが検証されていない取引の経験則（「勝率が高いから安定して儲かる」「年率ロールイールドはそのまま受け取れる収益」「パリティ残差がほぼゼロなら裁定機会がない」など）。

> 境界：本ディレクトリは研究記録であり、売買シグナルでも投資助言でもありません。すべての結論は明記した入力・パラメータ・口径に対してのみ成立します。

## 各ラウンドの進め方

### プロトコル

1. **先に登録、後に計算**：`rounds/<日付>.md` の冒頭に主張・操作化定義・判定規則・入力・パラメータを書いてから計算する。結果を見てから口径を選ぶことは禁止。
2. **再現可能**：正確なコマンド、入力ファイル/パラメータ、Python バージョンを示す。標準ライブラリかリポジトリ既存のツールのみを使う（第 6 ラウンドはリポジトリ `.venv` の pandas/AKShare）。すべての数字はコマンドから再計算できること。
3. **クロスチェック**：重要な数字は第二の方法で検証する（リポジトリのツール vs 独立実装、解析解 vs 数値、二つの復権口径など）。不一致は記録する。
4. **境界を明記**：どの仮定の下で成立/不成立かを書き、モデル水準と経験水準を分けて示す。
5. **1 ラウンド 1 主張**。
6. **台帳を更新**：ラウンド終了後に `claims.md` の状態・ラウンド・証拠リンクを更新する。変化がなくても「新しい結論なし」と書く。
7. **ツールの不具合は issue**：反証作業でリポジトリのツールのバグが見つかった場合、ここではコードを直さず、再現手順と file:line を付けて issue を立てる。

### ラウンド記録の読み方

| 節 | 内容 |
|---|---|
| 第 1–3 節 | 計算前に書かれた登録：操作化定義、判定規則、入力パラメータ、完全なスクリプト |
| 第 4 節 | スクリプトの完全な stdout（サンプル数、コスト列、試したすべてのパラメータ組み合わせ） |
| 第 5 節 | クロスチェックと実装の修正記録（回り道を直した経過を含む） |
| 第 6 節 | 判定 + 事前登録した判定基準の逐条対照 + 「証明していないこと」の明記 |
| 第 7 節 | 境界と未証明の部分 |
| 第 8 節 | フォローアップと次の候補 |

### 不正防止ルール

- 将来データを使わない。参照ウィンドウには起点を明記し、事後に調整しない。
- コストが関わる検証ではコストをモデル化し、「ゼロコスト」と「コスト込み」を別々に報告する。
- 複数のパラメータ/ウィンドウ/銘柄を試した場合は試行回数を報告し、最良の一つだけを載せない。
- データ源と取得日を記録する。合成データは `synthetic` と明記する。
- 「検証に通った」を「戦略が有効」と書かない。`SUPPORTED` は反例が見つからないことだけを意味する。

## 口径と境界

- **モデル水準 vs 経験水準**：F-001（Black-76 の反例）、F-003（合成カーブ）、F-009（数学的反例）は計算/公式を伴うモデル水準の反証。F-004–F-007 は文書レベルの証拠（リポジトリ文書が既に限界を明記、再計算はしていない）。F-002（バリアンス・スワップ代理データ）と F-008（A 株サンプル）は経験水準の判断。
- **コスト**：取引が関わるラウンドはゼロコストとコスト込みを別々に報告（F-001 0.10 ポイント、F-002 0/0.5/1.0 vol-point、F-003 0/2/5 bp、F-008 0/15/30 bp）。
- **多重比較**：F-008 は 3 つの閾値 × 3 つの保有期間を試し、すべて報告したうえで Holm 補正を適用。最良の組み合わせだけを載せることはしない。
- **代理口径**：F-002 は「ボラティリティ売り」をバリアンス・スワップで代理しており、オプション・チェーンの実際の満期損益ではない。実際の売り手 P&L はヘッジ誤差・ジャンプ・証拠金も負担する。
- **合成データ**：F-001/F-003 の入力は公式または `synthetic` データであり、文中で明記している。相場記録として扱わない。
- **市場結論を書かない**：`REFUTED` は「明記した口径の下で主張が成立しない」ことだけを意味し、現実の市場に edge がないことや売買助言を意味しない。

## 状態の定義

| 状態 | 意味 |
|---|---|
| `OPEN` | 登録済み、未検証 |
| `REFUTED` | 明記した口径の下で反例により反証（「主張が成立しない」） |
| `SUPPORTED` | 明記した口径の下で検証を通った（「反例が見つからない」であり、普遍的に成立する意味ではない） |
| `AMBIGUOUS` | 結果が口径/データに依存し、単一の結論を出せない。相違点を記録 |
| `BLOCKED` | データまたは権限が不足。何が足りないか、解除条件を明記 |

## ペース

DSH の定期タスク「取引モデル反証ラウンド」が**毎週火曜・金曜 21:00（Asia/Shanghai）**に実行します。各ラウンドで `OPEN` の主張を 1 件登録・検証し、ラウンド記録を書いて台帳を更新します。手動実行も可能です。2026-11-27 には第 1/3/4/5/6 ラウンドを 1 日で完了しました（第 2 ラウンドは F-002 の保留試行で、第 6 ラウンドが完了させました）。

## 主張の追加

`claims.md` に行を追加し、ID・主張原文・出所（どの文書/どの流行説か）・操作化定義・検証方法・状態を書きます。過去の結論を書き換えず、修正する場合は新しいラウンドを開いて「第 N ラウンドの修正」と明記します。操作化定義は再現可能なコードか公式に落とせる必要があり、できない場合は `OPEN` のままにします。

## リポジトリの他の部分との関係

- ツールの挙動契約は各 Skill の `references/` と `tests/` が基準です。本ディレクトリは「主張レベル」の反証だけを行います。
- [docs/validation.md](../docs/validation.md) との分担：あちらは「何を実装し、何を検証したか」、こちらは「どのモデル/仮定が反証され、どれがまだ成立しないか」を記録します。
